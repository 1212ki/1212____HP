# 1212 Homepage Admin

`tools/1212____HP/admin` は、1212ホームページの管理画面です。

## モード

- Local Mode
  - `data/site-data.json` を読み込み、保存時にJSONダウンロード
- API Mode
  - Cloudflare Worker APIへ保存し、LiveごとにX投稿（Web Intent + OGPリンクカード）可能

## タブ（5つ・Issue #47）

上の帯の下に、`Site` / `News` / `Live` / `Music` / `Profile` の5つのタブがある（#46までは6つで、`YouTube`と`Disco`が別々だった）。

| タブ | 編集するもの |
|---|---|
| Site | Home（顔にする作品・共有時の画像）・各リンク・Contactなど。タブ全体で1つの`保存して公開` |
| News | お知らせ。一覧から1件を開いて編集する |
| Live | ライブ・予約・Ticket Page共通設定（#46の流れのまま） |
| Music | 作品と映像。上の`作品`／`映像`で切り替える。映像の側にChannel URLの欄がある（旧Disco・旧YouTube） |
| Profile | 写真・文・SNSリンク。タブ全体で1つの`保存して公開` |

上の帯は薄く1行で、左に`1212 Admin`、右に接続の表示（API接続中は`接続中`）。ビルド標識（`ADMIN_BUILD_ID`）は画面の文字にせず、右の`title`属性に入れる。

## 運用

1. 編集するタブを選ぶ（Site / News / Live / Music / Profile）。News・Musicは一覧の行を押して1件を開く。幅899px以下は一覧→編集の2画面（編集の上の帯に`‹ 一覧`・題・保存の状態）、幅900px以上は左に一覧・右に編集の2列
2. `保存して公開`で反映する。保存の単位はタブごとに違う。Site・Profileはタブ全体、News・作品・映像は開いている1件、Channel URLはその欄だけ（開いている映像とは別の保存）。Liveは#46のまま（公演1件・Ticket Page共通設定）
3. 保存の状態は`保存済み`／`未保存`／`保存しています…`／`保存できませんでした`。`保存して公開`は未保存の変更がある時だけ押せる（スマホは画面の下に固定。幅900px以上は編集の見出しの右にあり、変更がない間は薄い）。入力して元の値へ戻せば変更なしに戻る。失敗した時は理由が`保存して公開`の上に1行出て、入力は残る
4. 新しいお知らせ・作品・映像は`+ 追加`から。何も入力しないまま`‹ 一覧`で戻る時は確認が出ない。保存するまで一覧には載らない
5. 削除は各編集面の`このお知らせを削除`などから確認の面（`やめる`・`削除する`）を経て、その場で保存して公開画面からも消える。顔にする作品を削除すると`自動（最新のリリース）`に戻り、再生する映像に選ばれている映像を削除すると、その作品の再生する映像が空に戻る（確認の面に件数が出る。戻りは削除と同じ1回の保存）。失敗した時は項目が一覧に戻り、編集面と入力が残る
6. 未保存のまま別の項目・`‹ 一覧`・`+ 追加`・作品／映像の切り替え・別のタブへ移ろうとすると、画面の中の確認（`保存していない変更があります。`・`破棄して移動`／`編集を続ける`）が出る。`破棄して移動`は入力を保存した内容へ戻す（保存はしない）。画像をアップロードしている間も出る。再読込・戻る・タブを閉じる操作はブラウザ標準の確認で止める
7. **API接続中はheaderに`保存`のボタンが無い**。全タブがその場の`保存して公開`を持ち、公開データ全体を送る入口は残していない。API接続失敗（読み取り専用）の時も出ない
8. Local Modeだけ、headerに`JSONを書き出す`が出る。各タブの保存はメモリへ反映して`JSON書き出し待ち`になり（headerは`JSONを書き出す *`）、`JSONを書き出す`でダウンロードして確定する
9. Live編集面の`告知`の`Xで告知する`でWeb IntentのXの画面を開く（投稿は自分で行う）。Liveの操作は下の「Liveの新しい流れ（Issue #46）」

画像は`画像を選ぶ`／`画像を変える`／`画像を外す`の3つの操作（全タブ共通）。選ぶとその場でアップロードされ、`保存して公開`までは公開データへ入らない。

### 保存の動き（Issue #47）

- 保存は`PUT /api/admin/site-data`の既存の経路（形・認証は変えない）。送る内容は「最後に読み込めた／保存できた内容に、その操作の対象だけを重ねたもの」。別の編集面の未保存の入力は送らず、入力もそのまま残る
- 入力はその編集面の中だけに持ち、保存が成功するまで公開データの手元の写しへ書かない
- Cloudflare Workerは変更しない（保存の経路・形・認証・検査は#46までと同じ）

### 既知の制限（Issue #47）

- 別の端末の保存を取り込む仕組みは持たない（最後に保存した側が残る。1人で使い、2台から同じ項目を同時に保存する頻度が低いため）。別の端末で保存したあとは、再読込してから編集する
- iPhoneのSafariなど、再読込・戻る・タブを閉じる時の標準の確認を出さない環境では、未保存のまま移ってもその確認は出ない（画面の中の移動は画面の確認で止まる）
- 作品・映像は、保存のたびに元のカテゴリから外れて保存先のカテゴリの先頭へ移る（カテゴリを変えない保存でも。#46までと同じ動き。並びは保存で変わる）
- Musicの映像の編集では、幅900px以上で`保存して公開`が2つ見える（Channel URLの欄と、開いている映像の編集）。対象が別で、押した方の入力だけが保存される
- 保存に失敗した直後の知らせ（toast）が、数秒のあいだ下に固定した`保存して公開`に重なる。理由は欄の上の1行にも出ていて、知らせは数秒で消える（#46のLiveと同じ動き）
- 画像を選ぶとその場でアップロードされる。保存せずに破棄しても、アップロード済みのファイルは残る（公開データには入らない）
- Local Modeの保存後の知らせは、幅390で左右にはみ出して見えることがある（共有の部品。ふだん使わない従来の運用）
- Ticket Page共通設定の保存が`ticket`を完了文と6項目だけに置き換える制限（#46）は、そのまま

## 設定

1. `config.example.js` を `config.js` としてコピー
2. `apiBaseUrl` にWorkerの公開URLを設定
3. `adminToken` をWorker側の `ADMIN_SHARED_TOKEN`（secret）と一致させる
4. 公開サイト側も `assets/js/site-config.js` の `SITE_API_BASE` を同じWorker URLに設定する

Cloudflare Accessで管理画面を保護する場合は、Worker側を `BYPASS_ADMIN_TOKEN = "true"` にして、`adminToken` を空にできます。


## 反映順序とrollback（Issue #47）

- GitHub Pagesが`main`から配信するので、mergeした時点で本番の管理画面が入れ替わる。**Cloudflare Workerは変更しないので、deployはない**（#46との違い）。新しい管理画面は、保存の経路・形・認証が今と同じなので、今のWorkerにそのままつながる
- merge前に管理画面のタブを開いていた端末は、旧版の`app.js`が残ることがある（旧版はWorkerと互換）。再読込で新版になる
- merge前の不具合: mergeしない。修理して確認し直す
- merge後の不具合（保存・削除が動かない、表示が崩れる、タブから戻れない）: 保存を止める（公開内容の更新は後にする）。#47の差分だけを戻すPRをOwnerが承認・mergeし、`?v=`と`ADMIN_BUILD_ID`で旧版の配信を確かめる。公開データの形・Workerは変えていないので、通常はコードを戻すだけで足りる（D1全体は巻き戻さない）
- 保存が誤った内容を公開データへ書いた時: 保存を止め、失われた更新と復旧の手段を示してOwnerが判断する。誤って削除した項目は管理画面で入力し直す（自動の復元はない）
- 版: `admin/index.html`の`ADMIN_BUILD_ID`は`2026-11-21T0300Z`、`style.css`・`app.js`・`music-data.js`の`?v=`は`20261121-47`。更新したらこの3つの`?v=`を揃える（`music-data.js`の中身は変えていないが、3つを揃える）

## 作品の選択・再生映像・種別（Issue #41）

※ 以下の「履歴」の各節は、各Issueの時点の記録。タブの名前や保存の経路が#47で変わった所には注記を付けた。今の操作は上の「運用」を見る。

SiteのHomeで「顔にする作品」を選択できます。Digital Release／宅録Demoの全作品から1件を選び、空の「自動（最新のリリース）」にも戻せます。保存先は`site.featuredReleaseId`です。画像の表示名は「共有時の画像」で、保存先`site.heroImage`とLive共有画像の予備としての働きを保ちます。

作品の編集には「種別」（`releaseType`、任意文字列）と「その場で再生する映像」（`playbackVideoId`、全映像カテゴリ共通のid）を追加しました。どちらも空にできます。従来のタイトル・説明・画像・リンクは保持します。新項目を欠く旧データは読込時にメモリ上で補い、通常保存時に永続化します。Local Modeの書き出しは従来のsite data本体で、APIの`data / meta` envelopeとは異なります。

新規作品と日付を変更した作品だけ、リリース日を空または`2025.05.05`の形で検査します。ASCII数字・ゼロ埋め・区切りの形だけを確認し、実在日や未来日の制約は追加しません。旧日付を変えずに別項目を編集・カテゴリ移動する操作はそのまま保存できます。不正な入力は日付の直下に表示し、入力と編集画面を保持します。API Modeの作品編集画面は保存成功後に閉じます（#47以降は、保存した作品の編集に留まります）。

選択中の作品を削除すると顔の指定を空に、映像を削除すると参照する全作品の映像指定を空に戻します。カテゴリ移動はidが同じなら参照を保ちます。削除内容は右上の保存（Local ModeではJSON書き出し）で確定します（#47以降、API接続中の削除は確認のあとその場で保存します。Local ModeはJSON書き出しで確定します）。API接続失敗時のread-onlyでも新項目を変更できません。

公開画面は#42でHomeに顔の作品・種別・選択映像の「聴く」を表示します。公開Musicの全作品・映像と作品の再生は#44、Ticket完了の案内は#43で扱います。作品はDisco、映像とChannel URLはYouTubeから編集します（#47でMusicに統合しました。作品は`作品`、映像とChannel URLは`映像`の側）。Homeの自動選択は、明示idがあれば優先し、それ以外は形の合う日付を持つ最新作品を選びます。同日はdigital→demoの元の順で、候補0件なら顔を表示しません。保存配列は並び替えません。管理タブの統合は#47で行いました。

### #41の反映と復旧（履歴）

GitHub Pagesは`main`の`/`から管理画面も配信します。Ownerが、試験済みPR最終revisionから先にWorkerをdeployし、Frontの公開API確認後にmergeします。Pagesのbuild・配信revision・app/helperの取得をFrontが確認してから管理タブを再読込し、Ownerが実際に使う1作品の3項目を保存して確認します。DB migration・新secret・既存データの一括更新は不要です。

merge前の不具合・merge見送りでは、OwnerがFrontの控えた直前Worker versionへ戻します。merge後は保存を止め、#41差分を戻すPRをOwnerが承認・mergeし、旧adminの配信確認後にWorkerを戻します。復旧中は作品編集を止めます。通常復旧でD1全体を巻き戻さず、実データ破損時だけ別途判断します。詳細は本cycleのCode Generation Plan §8・§9を参照してください。既存AI整理機能の反映順序はその機能の履歴として扱います。

## Liveの新しい流れ（Issue #46）

- 一覧（開催予定）の各行に`予約 N枚`と、未対応があれば`未対応 N`が出る（API接続中だけ。数えるのはキャンセルを除く予約）。集計が読めない時は一覧の上に`予約の数を読み込めませんでした。`、合言葉が通らない時は`認証できませんでした。`を1行出す。保存・予約の操作は妨げない。集計の読み取りが失敗しても、基準のAPIの切り替え（正式なURLへの再送）も読み取り専用への切り替えも起こさない
- ライブを開くと、スマホ（幅899px以下）は上の帯が`‹ 一覧｜日付と会場｜保存の状態`の1行になり、公開内容／告知／予約の切り替えが続く。公開内容はフライヤー→日付・会場→ライブ名→OPEN・START→料金→補足・共演者→`予約先・リンクなど`（折りたたみ）→`元情報から作り直す`（折りたたみ）→区分→`このライブを削除`の順
- `保存して公開`は未保存の変更がある時だけ、スマホは画面の下に固定で出る。幅900px以上は編集の見出しの右にあり、変更がない間は薄く押せない。入力して元の値へ戻せば変更なしに戻る。保存の状態は`保存済み`／`未保存`／`保存しています…`／`保存できませんでした`で、失敗の理由は`保存して公開`の上に1行出る
- 新しいライブは`+ 新しいライブ`→元情報を貼って`下書きを作る`（または`手入力で作る`）→内容を確認して`保存して公開`→`Xで告知する`の3つの操作で公開から告知まで進む。間に確認の面は出ない。保存の直後の告知の画面は、新しいライブの保存の時だけ出る（既存のライブは公開内容のまま`保存済み`になる）
- 予約は、ライブごとの一覧（合計・絞り込みの札・行）→予約1件（状態の操作）、`+ 取り置きを追加`、全ライブの`予約管理`（一覧→1件、`CSVで書き出す`）。幅900px以上は表になり、1件は表の右の面に開く。状態の変更・取り置きの送る内容・数え方は今のまま
- 削除は`このライブを削除`（文字）から確認の面（`やめる`・`削除する`。予約があれば件数を示す）を経て、その場で保存して公開画面からも消える。失敗した時はライブが一覧に戻り、編集面と入力が残る
- 未保存のまま別のライブ・一覧・タブ・`+ 新しいライブ`・Ticket Page共通設定へ移ろうとすると、画面の中の確認（`破棄して移動`／`編集を続ける`）が出る。再読込・戻る・タブを閉じる操作はブラウザ標準の確認で止める（iOSのSafariなど標準の確認を出さない環境では止められない既知の制限）
- Ticket Page共通設定は専用の画面（一覧の下の入口から。`‹ 一覧｜Ticket Page共通設定｜保存の状態`）で、その画面の`保存して公開`で保存する。入力は保存するまで公開データへ反映しない
- headerの`保存`は、API接続中のLiveタブでは出さない。他のタブ・Local Mode・他のタブに未保存の変更がある時は今のまま出す（#47で変更: API接続中は全タブでheaderに`保存`が無い。Local Modeだけ`JSONを書き出す`が出る）
- 上の外枠の接続の表示は、API接続中はHeaderの右に`接続中`だけを出し、接続の帯は出さない。帯はAPI接続失敗（読み取り専用。Headerは`API Fallback`）とLocal Mode（Headerは`Local Mode`）の時だけ出す。ビルド標識（`ADMIN_BUILD_ID`）は画面の文字にせず、Headerの右の`title`属性に入れる。他のタブの並び・表記・ほかの外枠は変えない（#47で、タブは5つ・上の帯は薄い1行に変わった）

### 保存の動き（Live・削除・Ticket Page共通設定）

- Live・削除・Ticket Page共通設定の保存は、公開データ全体を送る既存の保存（`PUT /api/admin/site-data`。経路・形・認証は変えない）のまま、送る内容を「最後に読み込めた／保存できた内容に、その操作の対象だけを重ねたもの」にする。別のタブの未保存の変更（headerの`保存`の待ち）は送らず、待ちも消さない（#47でheaderの`保存`は無くなり、別のタブの未保存は各編集面の入力として残る）
- 他のタブ（Site / News / YouTube / Disco / Profile）の保存（headerの`保存`と各画面の更新）は今のままで、公開データ全体を送る。別の端末の保存を取り込む仕組みは持たない（最後に保存した側が残る。既知の制限）（#47で、これらのタブも上の「保存の動き（Issue #47）」と同じ、対象だけを重ねた保存になった）

## 反映順序とrollback（Issue #46・履歴）

- GitHub Pagesが`main`から配信するので、mergeした時点で本番の管理画面が入れ替わる。一覧の予約の数のために`cloudflare/worker`に`GET /api/admin/ticket-reservation-summary`を1つ足した（追加だけ。詳細は`cloudflare/worker/README.md`）ので、**Workerを先にdeploy**し、本番の古い管理画面が今のまま動くことを確かめてからmergeする
- 新しい管理画面と古いWorkerの組み合わせでは、集計だけが`404`になり、一覧は予約の数なし＋`予約の数を読み込めませんでした。`の1行になる。保存・予約は変わらず動く。古い管理画面と新しいWorkerの組み合わせは、新しい経路を呼ばないので今のまま動く
- merge前の不具合・merge見送り: mergeしない。Workerの経路は追加だけなので、Worker自体に不具合がない限り戻さずに残してよい（戻す時は控えた直前のversionへ）
- merge後の不具合: 保存を止める（公開内容の更新は後にする）。#46の差分だけを戻すPRをOwnerが承認・mergeし、`?v=`と`ADMIN_BUILD_ID`で旧版の配信を確かめる。保存の経路・データの形・schemaは変えていないので、通常はコードを戻すだけで足りる（D1全体は巻き戻さない）
- 版（#46の時点）: `ADMIN_BUILD_ID`は`2026-11-20T1600Z`、`?v=`は`20261120-46`。今の版は上の「反映順序とrollback（Issue #47）」

## Live元情報からの下書き

Live編集の`下書きを作る`（新しいライブは元情報の画面、既存のライブは`元情報から作り直す`の中）はAPI Mode限定です。ブッカー／ライブハウスから受け取った元情報を貼り付けると、`date`、`title`、`venue`、`openTime`、`startTime`、`ticket`、`notes`、`performers`、`ticketUrl`、`link`の10項目を一括置換します。Local Modeでは利用できません。

- AIが空文字を返した項目も含め、10項目すべてを同じresponseから一括置換します。
- 貼り付けた元情報は変更・消去しません。
- AI整理後に人が内容を修正・確認し、通常の保存操作で反映します。自動保存・自動公開は行いません。
- 処理失敗時、または通信中に元情報や10個のフォーム項目を編集した場合は、AI結果をフォームへ反映しません。
- 確信度、根拠、別プレビューは表示せず、既存フォームを確認画面として使います。
- 実行中は`下書きを作っています…`、失敗した時は`下書きを作れませんでした。`と`入力した元情報と、今の入力内容は残っています。`を出し、元情報と各欄を残します。成功した時のprovider表示（`OpenAIで整理しました。内容を確認してから更新してください。`など）は変えていません。

## API接続失敗時

API Modeで管理APIの読込に失敗した場合、ローカルJSONをfallback表示します。この状態ではadmin全体がread-onlyになり、新規追加、入力変更、画像操作、保存、削除、AI整理、予約変更を行えません。headerの`保存`も出ません。既存のNews・Music（作品・映像・Channel URL）・Site・Profileの詳細は閲覧でき、グローバルタブやLive一覧・予約一覧のnavigationも利用できます（#46までの名前では、News・YouTube・Disco・Profile）。明示的なLocal Modeとは異なり、JSON書き出しへ切り替わることはありません。

## Live表示フォーマット

- 日付は`YYYY-MM-DD`で保存し、公開画面では実日付から曜日を計算して`YYYY.MM.DD(Day)`で表示します。解析不能な過去の保存値は画面に明示し、有効日付を入力するまでは別項目の保存で消さずに保持します。
- OpenとStartは別々に入力し、両方あれば`Open/Start: 18:30/19:00`、Startだけなら`Start: 19:00`と表示します。
- `ticket`はラベルを含めず料金・券種だけ、`notes`は`※`を含めず1補足1行、`performers`は本人を除く共演者を1組1行または`/`区切りで入力します。
- 公開表示は`ticket:`、`※`、`w. A / B`を自動で付けます。AI整理後も、原文と照合してから保存してください。
- 旧`description`は過去データ互換として保持されます（編集は`予約先・リンクなど`の中の`説明`。構造化項目が空のLiveだけで公開に使われます）。
