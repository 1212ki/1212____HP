# 1212HP System Design Principles

- Status: Approved
- Owner: Itsuki Matsumoto
- Last updated: 2026-08-16
- Applies to: 1212HP全体

## 1. 目的

1212HPは、公開サイトを見る人へ必要な情報を届けながら、管理者1名が迷わず短時間で更新・告知・予約対応を完了できるシステムとする。

設計書を実装の正本にし、画面やコードごとに判断が分散することを防ぐ。

## 2. 全体原則

### 2.1 公開サイトの構造をadminの外枠にする

adminの主要カテゴリは、原則として公開サイトの情報構造に対応させる。管理者が「公開画面のどこを更新するか」から入口を判断できる状態を維持する。

公開サイトにない運用機能は、関連する公開カテゴリの内側に置く。告知、予約対応、取込などの作業都合だけで、同格のグローバルカテゴリを増やさない。

### 2.2 各カテゴリの内側はタスク単位で整理する

公開カテゴリを選んだ後は、登録・編集・告知・予約対応など、管理者が完了したい仕事に沿って導線を組む。データ項目の羅列を画面構成にしない。

### 2.3 公開情報と管理専用情報を区別する

各入力・状態が「公開画面に表示される情報」か「管理だけに使う情報」かを画面と設計書の両方で追跡可能にする。

### 2.4 重要度と利用頻度で表示密度を変える

完了に必須で頻繁に使う項目を先に表示する。低頻度、詳細設定、履歴、例外対応は条件表示または折りたたみにする。すべての入力・ボタンを同じ大きさや強さにしない。

### 2.5 1つの概念に1つの正本を持つ

同じ情報を複数画面で編集できる場合も、保存先・優先値・反映先を1つに定める。公開URL、予約URL、Live詳細、告知文など意味の異なる値を兼用しない。

### 2.6 AIは元情報から再構成し、結果を確認可能にする

AI整理は、保存済みフィールドの有無に左右されず、保持した元情報を入力として対象フィールドを再抽出する。どの値を反映するか、再実行時に何を置換するか、失敗時に何を保持するかを機能ごとに定義する。

### 2.7 保存・公開・外部送信の関係を明示する

編集内容の保存、公開サイトへの反映、Xなど外部サービスを開く・送信する操作は、関係と失敗範囲を設計書で定義する。現在の1212HPではLiveの保存と公開反映は1つの`保存して公開`操作であり、Xへの遷移・送信や予約対応とは分離する。将来下書き機能を導入する場合は、保存先と公開状態を追加設計してから実装する。

### 2.8 mobileで主要運用を完了できる

主要操作はスマートフォンで完了可能にする。タップ領域は確保しつつ、ボタンや入力欄を常に全幅・大型にせず、関連する小操作はコンパクトにまとめる。

### 2.9 状態と失敗をその場で理解できる

保存中、保存済み、未保存、抽出失敗、外部遷移、予約状態などを対象の近くに表示する。失敗時は入力済み情報を失わず、再試行または手動対応へ移れるようにする。

## 3. 設計と実装の境界

- 仕様判断は `docs/specs/current/` に残す。
- `docs/plans/` は承認済み仕様を実装タスクへ分けるために使い、仕様判断の正本にはしない。
- `documents/` は旧来資料として参照できるが、現行設計と競合した場合はcurrent specを優先する。
- `DESIGN_RULES.md` は色、文字、余白、コンポーネントなどビジュアル上の共通制約として併用する。
- 実装が設計書にない判断を必要とする場合は、実装を止めて設計書を更新する。

## 4. 受入条件

- 新規・改修Issueが該当するcurrent specを参照している。
- 実装開始時点で該当設計書が `Approved` である。
- 公開画面とadminの編集箇所を追跡できる。
- 保存と公開の関係、および外部送信との境界が明示されている。
- desktop/mobile、失敗時挙動、検証方法が設計書に含まれている。

## 5. Canonical file map

- 文書体系と承認フロー: `docs/README.md`
- 現行設計の索引: `docs/specs/current/README.md`
- ビジュアルルール: `DESIGN_RULES.md`
- 実装計画: `docs/plans/`
- 旧来資料: `documents/`
