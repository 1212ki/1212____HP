## 1. 目的と範囲

ライブを知った人が、いつ・どこで・いくらかを確かめて、迷わず予約を終えられるようにする。Live一覧からTicket完了まで、通る画面は最短3つ（一覧 → Ticket → 完了）にする。今は送信中・失敗・完了がTicketの上に重ねて開く表示で、Ticket完了のページは使われていない。これをページ内の表示と、完了ページへの移動に作り直す。

対象は5画面の本文（`main`）で、Live一覧（`live/`）、Live詳細（`live/detail/?liveId=`）、終了したライブ（全件）（`live/detail/?view=past`）、Ticket（`ticket/`）、Ticket完了（`ticket/complete/`）。対応するJS・CSS・試験・設計書の更新を含む。

対象外（変えない）: ヘッダー・ナビ・フッター・Menu（#44が作ったもの）。Home・Music・Profile・Contactの本文。ただしHomeの次のライブで予約先のアドレスが正しくない時の1つの文言だけは、Live・Ticketと同じ「予約先を確認中」へ改める（Front判断。R43-06・Q43-01）。Homeのほかの表示・文言・構成は変えない。予約の受付とGmail自動返信の仕組み（#37）。料金の支払い方の表示（決まりを確認できていないので画面に書かない）。管理画面（#46・#47）。データの形・保存・Cloudflare Worker。

要件の正本は`docs/specs/current/public-site-ui.md`§2〜§7と`live-operations-admin-ui.md`§5.2。デザインの根拠はFigmaのLive・Ticket section `35:274`（画面10個、状態`29:249`の16個、要件メモ`29:347`）と部品`20:23`。原典・読取範囲・SHA-256は`aidlc-docs/audit.md`。Figmaのサンプル（ライブ名・日付・会場・料金・名前・メール・受付番号・作品名）は構造の見本で、掲載内容として採用しない。

画面の移動の数え方: Issue本文は「画面の移動は最短3回」、設計書と要件メモ`29:364`は「通る画面は最短3つ（一覧 → Ticket → 完了）」と書く。一覧から完了までの移動は2回で、Homeから数えると3回になる。設計書と要件メモを正とし、PS-L-01は「通る画面が一覧・Ticket・完了の3つ」で判定する。言い方の違いを理由にした仕様の変更はない。

## 5. 完了ページへ渡す内容（R43-10の詳細）

選択肢の比較と決定の理由はCode Generation Plan§2。決めたこと:

- 置き場所: `sessionStorage`のkey `1212hp_ticket_receipt_v1`に、受付内容を1件だけ置く。別のタブ・ブラウザ・端末には渡らず、タブを閉じると消える。名前・e-mail・備考をURL・query・hash・localStorageに載せない。
- URL: `ticket/complete/?liveId=<id>&rid=<受付番号>`。どちらも個人の情報ではない。URLと保存内容の`liveId`・受付番号が一致した時だけ表示し、別のライブ・別の受付のものを出さない。
- 保存内容: 版（1）、受付番号、`liveId`、保存時刻、対象Liveの日付・会場・タイトル・画像、名前・e-mail・枚数・備考（サーバーが返した受付済みの値）、送信時点の完了文・枚数と備考のラベル・表示設定。
- 消す時: 新しい送信を始める時、読む時に30分を過ぎている時、タブを閉じた時。再読み込み・戻る・進むでは消さない。
- 受付内容なし: 保存が無い、JSONが読めない、版が違う、必須の値が無い、期限切れ、URLと不一致、のどれでも「予約の受付内容を表示できませんでした。」。内容を作らない。
- 保存に失敗する環境（保存を禁止したブラウザ等）では、予約は成功したのに完了で「受付内容なし」になる。この場合は仕様どおり内容を作らない。Ticketは保存の失敗を無視せずに完了へ進む（予約の成功を失敗に見せない）。受付済みの控えはGmailの自動返信が残す（#37）。
