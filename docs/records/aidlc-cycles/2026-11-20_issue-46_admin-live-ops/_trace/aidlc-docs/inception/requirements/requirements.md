## 1. 目的と範囲

Itsukiが、新しいライブの登録・告知・予約の管理を、スマホから手間なく終えられるようにする。管理画面のLiveを、よくする3つの流れの順に作り直す。Itsukiはこの道具を毎日スマホで使い、mergeした時点で本番の道具が入れ替わる。**保存・削除・予約の状態変更を壊さないこと**を最優先にする。

対象は次のとおり（Issue #46の範囲、`audit.md` §1）。

- スマホでライブを開いた時の上の帯を1行にし、公開内容／告知／予約の切り替えを押しやすくする。
- フライヤーを公開内容のいちばん上に置き、「予約先・リンクなど」は折りたたむ。
- 「保存して公開」は未保存の変更がある時だけ下へ出す。削除はいちばん下の文字にし、確認のあとその場で保存する。
- 新しいライブの保存の直後に、告知の内容と「Xで告知する」を出す。
- 開催予定の一覧に、ライブごとの予約の枚数と未対応の件数を出す（Workerに集計を返す処理を新しく足す）。
- 予約1件を開いて状態を変える。取り置きの追加。全ライブの予約管理。
- Ticket Page共通設定は、その画面で保存する。
- 幅1440pxは、同じ中身を広げた形にする。

対象外は次のとおり。これらを変えないと満たせない要件が出たら、止めてFrontへ返す。

- Site・News・YouTube・Disco・Profileのタブの中身の作り直しと、タブを5つにすること（#47）。#47のタブの今の保存の動きは変えない。
- 公開側のページ（#42〜#45）、公開APIの応答、`assets/js/live-operations.js`の挙動。
- データの形（公開データのJSON、予約の保存の形）、DBのschema、予約の状態と数え方、元情報からの下書き作成（設計書§7の抽出契約・provider順・待ち時間）、告知の文の作り方（§8）、共有用のアドレス（§8.1）。
- 色・文字・余白の正本（`DESIGN_RULES.md`・`assets/css/1212-music.tokens.css`）。

要件の正本は`docs/specs/current/live-operations-admin-ui.md`（§2〜§6、§8〜§10、§11.2、§12.3、§13.3、§14、§15）。Figmaはマスタ section `15:20`（方針`43:491`、要件メモ`39:817`、状態`39:741`、よくする3つの幅390の12画面と幅1440の5画面）。原典・読取範囲・SHA-256は`aidlc-docs/audit.md`。Figmaの人名・会場名・件数・日付は見本であり、掲載情報として採用しない。マスタ・設計書・現行コードの食い違いと、描かれていない状態は`figma-fix-requests.md`（F46-01〜）に挙げ、採用値を決めた。
